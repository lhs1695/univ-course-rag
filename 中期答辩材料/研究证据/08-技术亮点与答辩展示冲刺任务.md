### P0：把技术贡献讲清楚并落到候选 PPT

直接产出 `中期答辩材料/汇报PPT/中期汇报-v6-candidate.pptx` 和配套 `讲稿-v6-candidate.md`。如当前工具链不能可靠生成/编辑 PPTX，先产出逐页内容完整、可直接制作为 PPT 的 Markdown/页面规格，并明确工具限制；不要只交建议。

建议控制在 8–10 页、6–8 分钟。叙事按「真实痛点 → 系统方案 → 技术机制 → 真实证据 → 失败与边界 → 中期结论」推进。至少让评委一眼看到以下四个有工程含量的亮点：

1. **课程边界贯穿访问链路**：角色/课程授权不是 UI 装饰；结合代码路径和已验证 PERM 截图，解释未授权请求如何被拒绝。只描述代码与测试实际覆盖的范围。
2. **从课件到原文的证据链**：PDF 页级解析与质量状态 → 按课程检索 → 受限生成与有效引用 → 引用打开原 PDF 对应页。用现有架构图、问答链路图和真浏览器截图展示，不要只列技术栈。
3. **失败语义与安全降级**：有据回答、依据不足、系统/上游故障、权限拒绝是不同状态；用 LA-01、LA-R、系统故障重试和 PERM 证据串成一个可视化对照。强调「系统没有证据」不等于「系统坏了」，也不等于「答案一定正确」。
4. **可审计的评测与质量门禁**：27 份 PDF / 2,501 chunks、`COVERAGE_INCOMPLETE` 的解释、22 题 Dense/Hybrid 小样本对照、逐题证据与 usage 记录。展示研究过程如何发现问题、保留失败，而不是只展示漂亮数字。

技术页避免泛泛罗列 FastAPI、Vue、PostgreSQL、Embedding 等组件。每个亮点必须回答：解决什么痛点、关键机制是什么、现有证据是什么、边界是什么。可使用架构图/链路图/截图/少量指标卡；避免密集段落和过多文字。不要为了“技术感”新增 Agent、知识图谱、重型解析器或其他没有验收时间的功能。
