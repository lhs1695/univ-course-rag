## 1. 为什么做第六期

第五期已经解决单实例代码中的失败边界、解析资源预算、readiness 与 CI，但还不能将“可在开发机运行”表述为“可部署”。若要让外部试用者通过 HTTPS 访问，需要先明确单台主机、域名、反向代理、持久化目录、数据库备份和恢复责任。本期将这些条件变成受限、可复现、可演练的单主机交付，而非扩建生产平台。

这条线对 Python 后端岗位也更有价值：它要求把应用配置、网络边界、容器运行身份、数据库迁移和灾难恢复写成可验证合同，而不是只展示本机 `uvicorn --reload`。

## 2. 本期目标

1. 在写部署代码前明确唯一的部署目标、责任人、域名/TLS、数据库与上传文件的持久化位置，以及可接受的数据恢复目标。
2. 为生产模式设置显式、可校验的安全配置边界，避免用开发默认值公开运行。
3. 提供仅面向单主机的可重复构建与启动说明，应用和数据库均不以 root 身份运行，上传文件与数据库数据均持久化且不进镜像。
4. 提供不含秘密或课件内容的数据库备份、恢复和迁移演练流程，并证明恢复后核心检索数据可读。
5. 提供反向代理/TLS/health-readiness 的运维模板与上线、回滚检查表；真实上线只在维护者另行授权后执行。

## 3. 全期边界

- **只做：** 单台主机、一个 Postgres 实例、一个应用实例、受控上传卷、HTTPS 入口、备份与人工恢复演练。
- **不做：** Kubernetes、多实例、负载均衡、对象存储、Redis、Celery、定时任务平台、CAS/OAuth、多租户、自动扩缩容、监控集群、云密钥托管或自动部署。
- **不重开：** JWT/localStorage、模型供应商、课程权限、检索/引用语义、阶段 25 的真人试用，以及阶段 18/19 的反馈触发条件。
- **安全底线：** `.env`、备份、上传卷、Cookie、Session ID、真实课件、真实问答和日志不得进 Git 或聊天；部署文档只使用占位域名、占位路径和脱敏示例。

## 4. 开工门槛

阶段 38 的部署合同必须记录下列事实；任一缺失则本期停在文档阶段，不实施部署：

| 必须确认 | 最低要求 |
| --- | --- |
| 主机与责任 | 单台 Linux 主机、维护者、补丁/故障响应责任明确 |
| 入口 | 受控域名或明确的仅内网访问边界；TLS 证书来源与续期责任明确 |
| 数据 | Postgres 数据卷、上传卷、备份目标和访问控制明确 |
| 恢复 | 可接受的 RPO/RTO 由维护者确认；有可用的非生产演练环境 |
| 访问范围 | 允许哪些用户访问，是否允许外网；若只用于本机或临时演示，本期不部署 |

## 5. 分阶段

### 阶段 38 — 部署合同与威胁边界（下一阶段）

- **做：** 新增 `docs/deployment-contract.md`，以无秘密占位符记录单主机、维护责任、访问边界、域名/TLS 责任、持久化路径类别、备份目标、RPO/RTO、升级窗口和回滚责任。对公开入口、Cookie、上传文件、数据库、反向代理和供应商 API 写出最小威胁模型与拒绝项。明确是否满足本期后续开工门槛。
- **不做：** 不创建云资源、不申请域名/证书、不连接生产数据库、不写 Dockerfile 或代理配置、不把“计划使用 HTTPS”伪称为已启用。
- **证明：** 文档中的每一项都有维护者确认值或明确标为“未满足”；`git diff --check` 通过。若任一门槛未满足，提交文档并停止，等待外部条件。

### 阶段 39 — 生产配置与浏览器安全边界

- **前置：** 阶段 38 全部开工门槛已满足。
- **做：** 引入显式运行环境配置与启动前校验：生产模式拒绝开发 Cookie 设置、通配 CORS/origin、空的可信入口或不安全的必填配置；将 Cookie `Secure`、`SameSite`、可信 Host/origin 等行为绑定到已确认的部署合同。保留本地开发与 Fake pytest 的确定性默认值。为配置错误提供稳定、不泄露值的失败信息。
- **不做：** 不改 JWT/localStorage，不把 `.env` 值写入日志，不用“自动猜环境”代替显式配置，不在测试中读取本机 `.env`。
- **证明：** 配置单测覆盖开发默认、生产合法配置和每类关键非法组合；受保护 API 的 Cookie 属性与 origin 拒绝行为有测试。运行直接相关 pytest 与仓库根 `python -m ruff check`。

### 阶段 40 — 单主机可重复运行工件

- **前置：** 阶段 39 完成，且阶段 38 的持久化目录与权限责任已确认。
- **做：** 提供独立于开发 Compose 的生产启动工件：固定 Python/Node 构建版本、非 root 应用进程、只读代码层、受控写入上传卷、Postgres 数据卷、health/readiness 检查和最小端口暴露。记录镜像/依赖锁定、迁移顺序及失败时停止策略。
- **不做：** 不把 `.env`、上传内容、数据库或前端开发依赖打入镜像；不暴露 Postgres 到公网；不在镜像构建中调用模型供应商；不取代本地开发流程。
- **证明：** 在隔离的本机 Compose 环境从空卷启动，运行 `alembic upgrade head`、`python -m app` 等价 seed 与 `/health`、`/ready` 检查；容器内以非 root 用户运行；`docker compose config`、相关 pytest、Ruff 与前端构建通过。测试数据仅用夹具/Fake。

### 阶段 41 — 备份、恢复与迁移演练

- **前置：** 阶段 40 的持久化卷和运行工件通过证明。
- **做：** 编写人工触发的数据库备份、校验、保留和恢复 runbook；明确上传卷与数据库备份的一致性限制及可接受的恢复窗口。增加不接触真实数据的演练脚本或可复制命令，证明从空数据库恢复后能迁移至 head，并用夹具验证课程、资料元数据和 pgvector 检索路径可用。
- **不做：** 不上传备份到第三方服务，不把备份放进 Git，不假称文件系统快照与数据库事务天然原子，不引入自动定时备份服务。
- **证明：** 使用一次性测试数据库/卷完成“备份 → 清空隔离目标 → 恢复 → upgrade head → 标记 Postgres 检索测试”；备份产物不进入工作树，日志不含课件正文、Cookie 或 key。运行对应 pytest 与 Ruff。

### 阶段 42 — 入口模板、上线与回滚 runbook

- **前置：** 阶段 41 演练通过；真实域名、TLS 续期责任和访问范围仍有效。
- **做：** 提供反向代理的最小模板与变量清单：TLS 终止、HTTP 到 HTTPS 的策略、上传大小一致性、`/health` 与 `/ready` 探测、应用端口不直接公开、日志脱敏和错误页策略。编写上线前检查、升级、回滚和事故处置 runbook，并标明哪些动作需要维护者在目标主机手动执行。
- **不做：** 不直接修改真实 DNS/证书/防火墙，不自动部署，不加入监控 SaaS，不以 0 停机或高可用为承诺。
- **证明：** 模板在本机以占位域名通过语法检查；runbook 能从空环境逐项执行到健康检查。只改文档/模板时运行 `git diff --check`；若改应用配置，补跑其直接测试与 Ruff。

### 阶段 43 — 受授权的试运行与第六期收口

- **前置：** 阶段 42 完成，且维护者明确授权目标主机、访问范围和操作窗口。
- **做：** 在授权环境按 runbook 进行一次最小试运行：验证 HTTPS、Cookie、登录、课程隔离、上传/删除、问答拒答、引用、`/health`、`/ready`、备份与回滚检查。记录仅含状态、版本、request ID 和脱敏故障分类的结果；更新 README、INDEX、NEXT-SESSION 与本计划。
- **不做：** 不用真实学生身份做验收，不调用真模型作为自动门禁，不将阶段 25 伪装成部署试运行，不根据一次试运行宣称高可用或正式校园网生产。
- **证明：** 维护者签字/确认的脱敏验收记录、工作区与敏感文件审计、CI 成功和至少一次恢复演练证据。未获授权时只停在阶段 42，不执行本阶段。

## 6. 顺序与停止条件

**38 部署合同 → 39 配置边界 → 40 运行工件 → 41 恢复演练 → 42 入口/runbook → 43 授权试运行**。

阶段 38 若未满足任一外部条件即为本期合法停止点；不得以代码实现替代主机、TLS、备份责任或维护者决定。阶段 43 后也不自动扩展到多实例、队列或云平台，规模或真实使用需求出现时另立第七期计划。
