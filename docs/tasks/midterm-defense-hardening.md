# 中期答辩冲刺任务提示词

> 目标：在距离大创中期答辩约两周时，集中提高研究证据可信度、项目技术叙事、演示稳定性和材料一致性。本文可直接交给项目主 Bot 执行。

## 给执行 Bot 的指令

你是本项目的主执行 Bot。请直接接管这轮中期冲刺：先核实事实，再自主排序、实施、测试和整理交付物。**不要只给建议或再写一份计划；能安全完成的工作应直接完成。** 发现实质问题时优先修复并提供验证证据，不要为了“技术亮点更多”而扩张项目范围。

用户允许为中期目标做必要的代码修复和小范围功能改进，时间约两周。你的首要目标是提高验收可信度，而不是追求功能数量。遇到非关键选择，自行采用风险最低且可验证的方案；仅在涉及不可逆数据操作、明显额外费用、外部发布或无法绕开的关键歧义时暂停该项，并继续其他不受阻的工作。

## 一、开始前必须核实

1. 在仓库根目录检查 `git status`、分支和近期提交。保护现有未提交改动，不得用 reset/checkout/restore 覆盖它们；不要默认 push、部署或批量暂存无关文件。
2. 读取根 `AGENTS.md`、`docs/当前交接.md`、`docs/validation.md`、`docs/engineering.md`、`docs/evaluation-results.md`、`docs/中期演示运行卡.md`、`新开题资料.md` 及中期答辩材料中的提纲、讲稿、PPT 和彩排摘要。只补读与具体问题有关的代码和证据，不要无目的地重读全仓。
3. 区分“最初提交/获批的开题材料”和后来修订的 `新开题资料.md`。查找仓库内可用的原始材料；若找不到，明确记录这一限制，不要把修订稿冒充原始承诺。
4. 所有结论以当前代码、数据库和可复核记录为准。历史数字、Fake 测试、弱规则命中、AI 预标结果均不得包装成人工事实正确率。

## 二、固定事实与项目边界

- 工作区：`D:\workspace\univ-course-rag`。
- 中期正式演示库：`univ_course_rag_cn_v2`，目标口径为 4 门中文课程 / 27 份 PDF / 2,501 chunks；课件位于 `corpus/local/cn-replace-2026-10-18/rechunk/uploads_v2/`。执行前重新核实，若事实变化以实际结果为准。
- 课程：线性代数、概率论与统计学、人力资源管理、教育学原理。
- 当前演示默认 Dense，reranker 关闭；生成模型为 DeepSeek `deepseek-flash`，Embedding 配置为 BGE-M3。除非新实验有充分证据，不要改变中期默认配置。
- 现有 `12/12` 可答题预期文档/页命中与 `4/4` 拒答属于弱规则/AI 预标验收，不是人工事实正确率，也不证明引用一定支持答案。
- Docling 全量解析路线已停止。生产 PDF 保持 PyMuPDF 轻量路径；不引入新的重型解析器，不做全量 VLM 入库，不为中期重建 RAG 平台。

## 三、工作优先级

### P0：建立可信的研究证据

1. 盘点当前题集、已有真实运行结果、评测脚本和报告，确认哪些结果可复现、哪些只是结构性/弱规则验收。
2. 设计一套小而有代表性的人工核验题集，建议 20–24 题、四课均有覆盖。至少覆盖：课内事实、术语/措辞差异、跨段或跨页问题、依据不足问题。每道可答题在看模型输出前记录预期文档/页码与必需要点；拒答题明确说明为什么课程资料不应回答。
3. 对代表性答案分别检查：事实要点是否正确、引用原文是否真正支持答案、来源页是否正确、依据不足是否正确拒答。引用存在不等于引用支持，检索命中也不等于答案正确。人工核验者、核验范围和判定规则必须记录；若无法安排独立核验，明确标注为开发者核验。
4. 在不污染正式演示库的前提下，评估 Dense 与 Hybrid 是否值得比较。先检查现有检索实现和候选融合路径，尤其核实关键词独有候选是否在后续被分数门槛过滤。优先记录候选召回、最终证据、引用支持、延迟和失败类型；不要只凭单次问答观感判断优劣。
5. 只在可解释、可复现的条件下运行小样本真实评测。复用当前正式库和已有向量；禁止为这项任务全量重入库。每次真实模型调用记录模型身份、题数、实际 usage/费用证据（可获取时）和失败情况；不猜测费用。若当前授权范围或费用边界不明确，不执行新增收费调用，先完成离线准备并在交付中明确指出需要的最小授权。
6. 保存版本化题集、标注说明、运行命令、结果摘要和失败案例。不得只保留漂亮的汇总数字；结果不理想也如实报告，不调题、不改标签来制造优势。

### P1：调查并改善资料解析质量的可解释性

1. 当前数据库曾观察到 27 份资料中 20 份带有 `COVERAGE_INCOMPLETE` 警告。重新核实现状、警告生成规则、页级解析报告和原始 PDF；该警告是需要调查的信号，不等同于 20 份资料解析失败。
2. 对风险较高且与演示题相关的代表页面做原文对照，至少关注公式密集页、图文/表格页、稀疏页和引用演示页。记录原页、提取结果、页码映射、是否影响实际问答，以及现有能力的明确边界。
3. 如果现有数据足以支持准确解释，可小幅改善教师资料页的质量提示，例如说明“部分页面需核对”并展示可验证的原因；若没有页级信息支撑，不得编造页码、质量分或“已完整解析”状态。
4. 只有在具体缺陷已确认、修复范围小且能在本轮验证时才改解析代码。不要为消除警告而放宽质量门禁、静默忽略异常或重跑全部入库。

### P2：演示可靠性与失败路径

1. 按现有运行卡复核正式演示环境、库、资料目录、模型配置和固定问句；不得临场更换模型、启用 reranker 或重新入库。
2. 核实并补齐以下路径的可复现证据：正常回答与引用回原 PDF 页、依据不足、系统/上游服务失败、未授权访问被拒绝、教师资料状态/反馈页面。
3. 检查错误状态是否被准确区分：系统故障不能伪装成依据不足，权限失败不能显示成功，引用存在不能暗示答案已被证明。发现问题时优先修复小而明确的缺陷，并运行直接相关测试。
4. 整理真实浏览器截图与 3–5 分钟演示录屏所需的脚本/检查单。所有材料不得出现 API Key、Cookie、真实口令或其他敏感信息。无法实际录屏时，明确列出需要负责人手工完成的步骤，不得声称已录制。

### P3：技术叙事、开题承诺与材料统一

1. 将核心叙事统一为一个问题：**如何让高校课程问答不仅生成答案，还能遵守课程边界、提供可核对依据，并在依据不足时正确停止？**
2. 优先围绕三条已有实现且有证据支撑的贡献组织讲解：
   - 课程与角色授权边界；
   - 从资料来源/页码到检索证据、回答引用和原文核对的可追溯链路；
   - 依据不足、系统故障和权限拒绝的状态区分，以及对应的验证方式。
3. Dense/Hybrid、重排、教师问答反馈、解析质量门禁等内容只能按真实实现和实测证据描述；不要把“使用某个技术栈”直接写成创新点，也不要宣称尚未证实的检索收益。
4. 对照原始开题承诺检查扫描页、公式、表格、图片/图表能力的中期范围。如果原始承诺确实要求中期验证代表性复杂页面，优先复用现有工具做一个极小、固定、可复核的专项样本；不新增重型解析器，不默认全量 Vision，不将专项结果外推到所有资料。如果原始承诺无法确认，明确写出证据缺口。
5. 统一 `新开题资料.md`、`中期答辩材料/答辩提纲.md`、讲稿、PPT、README、运行卡与评测登记中的课程、模型、数据规模、指标口径、已完成能力和限制。PPT 保留原 `v5` 作为参考稿，若要实质修改，另产出清晰命名的候选版本，不静默覆盖参考稿。
6. 最终材料应能清楚回答：解决了什么问题、为什么技术路径合理、做了什么对照/验证、证据支持什么、当前限制是什么。避免空泛的“高准确率”“显著提升”“通用多模态”等表述。

## 四、执行约束

- 先做证据审计，再做改动；按 P0 → P1 → P2 → P3 排序。若某项依赖外部条件，先记录阻塞并继续其他项，不要停在长计划上。
- 允许在本机工作区进行必要的代码、测试、评测脚本、报告和答辩材料修改。一次完成一个有明确验收标准的子任务；每项验收后按根 `AGENTS.md` 进行本地 Conventional Commit。不要 push。
- 任何真实数据库写操作、迁移、删除资料、全量重入库、重型依赖安装、外部发布均不属于默认授权。优先只读和隔离副本；必要时先说明具体风险、备份/恢复方案与最小授权范围。
- 真实模型调用仅限小规模、必要的实验，不做全量 Embedding 或全量 Vision。严格遵循当前 `AGENTS.md` 的云调用授权要求；授权或成本边界不明确时，完成本地可完成的工作后再报告，不要自行扩大调用范围。
- 不为“看起来先进”而加入 Agent、知识图谱、复杂多模态流水线或新平台；不把重排设为演示默认；不删除历史证据或清理 `corpus/local/`。
- Python 使用 `backend/.venv`；代码变更运行相关测试、Ruff，前端变更运行构建和直接相关测试。纯文档变更检查链接、口径一致性与 `git diff --check`。
- 不得伪造测试结果、人工标注、截图、录屏、usage、费用或用户试用结论。失败和未完成项必须留痕。

## 五、最终交付与验收标准

完成后必须提供简明但有证据的汇报，并在仓库中留下可交接材料：

1. **现状与风险清单**：按高/中/低优先级列出真实发现，附代码/文档/测试/结果路径；区分已修复、已验证、未解决和不在中期范围内。
2. **研究证据包**：题集与标注规则、运行命令、可复核结果、失败案例、方法限制。没有真实模型授权或人工核验条件时，明确说明缺失，不能用 Fake 结果代替。
3. **代码/质量改进**：只提交有明确收益的最小变更，列出测试命令和真实结果；若确认无需代码改动，说明证据，不为完成任务而造功能。
4. **答辩材料候选**：提纲/讲稿/PPT 口径统一，研究贡献和数据指标均有证据指向；原参考稿保留。
5. **演示交接**：最终环境核对清单、固定操作步骤、失败降级方式、截图/录屏状态及负责人需要手工完成的事项。
6. **收尾状态**：列出本地提交号、工作区状态、未完成项及其原因。没有实际运行的测试不能标 PASS；没有实际完成的演示/录屏不能标完成。

**总验收原则：** 两周内以“更可信的研究证据 + 更稳定的演示 + 更一致的答辩叙事”为完成标准，不以新增功能数量或文档数量为标准。自主推进、及时验证、如实汇报；遇到不确定性先缩小范围并保留证据，不要用未经验证的结论填补空白。
