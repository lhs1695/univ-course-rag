## 目标与约束

面向高校各类课程，采用开源组件完成有依据、可核对的问答与课程适配。中期交付本机原型，结题争取小范围多人试用。中期前须验证普通文字、扫描页、公式、表格和图片/图表的有限代表样本；不要求建立任意格式、任意复杂页面的通用多模态平台。工程目标是**尽快用成熟开源能力补齐当前解析短板，而不是增加一个新的 RAG 平台**。

## Docling 稳妥型开工计划

这一节是给 Cursor 的实际施工顺序。用户负责决定真实云调用、较大依赖/模型下载、数据库迁移等有实际成本的动作；Cursor 不自行跨项施工。除明确授权外，本阶段不读 `.env`、不调用真实 embedding/LLM/Vision/reranker、不重新入库、不删除旧结果。

### R7B-1：代表页离线验证

**目标：** 先证明 Docling 在本项目真实资料上“值得接”，而不是先改生产代码。

1. 从已冻结的 17 份 PDF 中固定约 12–16 页，至少覆盖：正常文字、多栏/版面、心理学纯图像或扫描页、线性代数公式、表格、历史地图/图表、图文混排。运行前固定页清单，不因结果好坏替换样本。
2. 在现有 `backend/.venv` 中按当前 Python 依赖管理方式加入**最小必要 Docling 依赖**并固定版本；不安装 `all` extras，不下载无关模型，不启动 Docling Serve，不建立第二套环境。实际安装前记录预计磁盘/下载成本；若解析所需模型超出本机可接受范围，先停在本项并汇报。
3. 使用 Docling 官方 Python API 或 CLI 做离线转换，优先产生结构化 JSON 和可读 Markdown/文本视图。代表页验证可以使用页范围参数，避免为了测试 12–16 页而处理整套 344 页。
4. 逐页人工核对：阅读顺序、缺字/重复、页眉页脚、OCR、公式结构、表格关系、图片/图表发现、页码和 bbox。不要用字符数或 Markdown 是否生成作为质量结论。
5. 同时记录工程成本：包版本、模型身份、下载体积、安装时间、CPU/GPU、峰值内存、逐页耗时、失败和降级。模型许可与 Docling 代码许可分开记录。

**通过门槛：** 关键来源页号不丢；扫描/图像页至少能形成可读 OCR；代表公式没有系统性结构错误；表格至少保留可核对的结构；图片/图表至少被正确发现并能回原页；本机能稳定重复运行。单项小误差可以登记，不要求宣传级完美。

**失败处理：** 若出现页/来源丢失、代表公式系统性错误、关键视觉页无法核对或环境无法稳定复现，R7B-1 失败；不得直接进入适配。只有这时才启动 MinerU 针对同一 blocker 的后备验证，不在本项并行维护两套生产管线。

### R7B-2：Docling 薄适配器

**目标：** 将 Docling 接进现有 ingestion，而不是把项目改造成 Docling 应用。

1. 保留现有上传、课程权限、任务租约、失败恢复、原子替换、Postgres/pgvector 和问答链路；只替换“文件内容 → 解析单位”的入口。
2. 建立最小项目级解析结果：`Document → Page → Element`。元素至少区分 `Text / Formula / Table / Image / Chart`，并保存 `page`、`bbox`（可得时）、`extraction_method`、`parser_version`、`model`（可得时）、`status` 及受控 `asset_ref`。
3. `native_text`、`ocr`、`formula_recognition`、`image_description`、`chart/table_extraction` 必须区分；机器派生结果不能伪装成原文。
4. Markdown、TXT 继续走现有轻量文字路径；R7B 首先替换 PDF。DOCX/PPTX 是否切到 Docling，只在 PDF 适配稳定后检查现有代码复用价值，不为了“统一”增加额外风险。
5. 不直接把 Docling JSON 字段散落到业务模型；不引入 LangChain、LlamaIndex、RAGFlow、RAG-Anything 或新的数据库。

**验收：** Fake/离线夹具能验证正常页、OCR 页、公式/表格/图片元素和失败状态；现有解析/切分/入库合同未被无关改动破坏；Ruff 与当前项测试通过。

### R7B-3：页级质量、来源和失败状态

**目标：** 让“解析成功”变成可解释状态，而不是一个布尔值。

每份资料至少形成：总页数、成功/异常/空页、页号连续性、每页耗时、元素类型计数、解析方法、parser/model identity、结构化产物哈希和关键异常。关键元素能回原 PDF 页；有 bbox 时进一步支持页内区域。

解析 `PARTIAL/FAILED` 不得映射成 ingest `succeeded`。只有结构化解析、切分、索引和来源元数据全部满足合同时才原子替换旧片段；新解析失败必须保留旧完整索引。

### R7B-4：17 份四课离线解析冻结

**目标：** 在不调用云模型、不写数据库的情况下，把 17 份 PDF 变成一套可恢复的解析基线。

1. 用唯一 Docling 主解析器处理 344 页资料，固定 parser/version、实际启用能力、模型/version 和运行配置。
2. 生成结构化解析事实源、页级质量报告、图片/图表/表格/公式素材清单及 SHA-256/产物哈希。真资料和中间产物只放 `corpus/local` 等受控忽略区，不进 Git。
3. 对异常页逐项登记原因，不以“整份文件总体文字量正常”掩盖局部漏页。
4. 根据冻结结果判断每课可支持的题型；不能稳定解析的内容标记为限制，不为了凑题数把失败资料算进成功能力。

### R7B-5：题集与工具 dry-run

固定四课题集，每课先约 6–8 题，实际数量服从解析后可用内容。每题提前记录必需要点、支持文档/页或区域、是否应拒答和知识点隔离。先运行 Fake/dry-run 检查题集、来源、解析/切分/索引身份、预算、checkpoint 与恢复逻辑；不执行真实模型。

### R7B-6：受控入库与每课小样本

在用户明确授权数据库迁移/重入库后，先备份并核对目标库，再按四课分别入库。每课先用少量开发题检查“解析 → 切分 → embedding → 检索 → 来源”链路；确认无串课、索引身份匹配、失败可恢复后，才进入正式基线。不得因为旧库已有数据而跳过新解析身份检查。

### R7B-7：四课新基线

固定资料、题集、解析版本、切分、embedding、prompt、证据预算和生成模型。顺序保持 `dense → hybrid → hybrid + rerank`；先重新校准当前阈值，再决定是否需要 reranker。默认不启用 reranker，不为了中期“技术完整”强行加入。

主基线不默认把图片发送给 DeepSeek。若确有视觉题，在另一轮明确授权下只选少量固定页面/题目发送 Vision，并将视觉结果与纯文字 RAG 指标分开。

## P7 中期产品化收口

P7 不是第二轮大开发，而是把已经存在的课程、问答、资料和管理能力收成一个可演示、可恢复、可解释的中期版本。中期不要求生产级容量、完整注册体系、多人公开服务或任意复杂多模态能力。原则是“核心 RAG 做实，外围产品做完整，非核心能力不膨胀”。

### P7-1 前端成品化

1. 保留 Vue 3 + Element Plus，不更换 UI 框架、状态管理或 PDF 技术栈。
2. 优先打磨学生问答页：问题输入、回答状态、引用卡片、依据不足/系统失败、引用聚焦、原 PDF 页定位形成清晰的单页学习工作台。
3. 统一课程、资料、成员、反馈和管理页面的标题层级、间距、卡片、按钮、状态标签、空/加载/错误状态；小屏保证基本可操作。
4. 课程资料页明确显示解析/入库状态、失败/异常提示和重试入口；不把解析器内部细节全部暴露给学生。
5. 不实现完整 PDF.js 阅读器、不做动画/主题系统/移动端 App，不为视觉包装引入大型前端依赖。

**验收：** 核心页面视觉一致；学生能够完成“进入课程 → 提问 → 看回答 → 点引用 → 回原 PDF”的操作；失败、空状态和权限失效不会显示成成功。

### P7-2 课程与学生生命周期

现有模型和 API 已支持管理员创建课程、管理课程成员，教师在课程内加入已有学生，学生在“我的课程”进入已授权课程。因此中期采用最简单的受控流程：

管理员创建课程/账号 → 管理员或教师加入已有学生 → 学生进入我的课程 → 教师上传资料 → 学生问答

1. 不新增学生自主选课、公开课程目录、邀请码、申请审批等非核心流程。
2. 补齐管理员侧课程编辑/删除入口（后端已有能力时优先做 UI 闭环），删除需二次确认。
3. 课程成员变更必须立即影响下一次请求；学生只能访问当前已加入课程。
4. 教师只能维护自己有权限的课程；管理员维护课程和账号。
5. 不把课程/学生统计扩展成成绩、能力画像或个性化推荐。

**验收：** 至少用管理员、教师、学生三种角色各走一遍创建/授权/访问/撤权链路；课程删除不留下可访问的课程内容。

### P7-3 数据库与文件生命周期收口

1. 不更换 PostgreSQL + pgvector，不引入 Redis、Elasticsearch、MongoDB 等新基础设施。
2. 核对最新 Alembic migration 可从干净数据库建立；真实目标库在实施前单独确认迁移状态。
3. 核对课程、成员、资料、Chunk、问答记录的外键和删除语义；课程/资料删除不能留下可检索或可直接读取的旧内容。
4. 保持“数据库记录”和“上传文件”分开恢复；文件清理失败记录补偿状态，不在请求内无限重试。
5. 解析产物以受控本机文件作为事实源/恢复材料，业务库保存必要 metadata、来源、Chunk 和向量，不把完整解析 JSON 与所有图片二进制塞进 PostgreSQL。
6. 中期至少形成一次数据库 dump + 上传资料/解析产物恢复包，并在冻结前验证恢复；不使用 Docker volume 清空重建作为“恢复”。
7. 准备可重复的 Demo 数据恢复/重置流程；它只操作明确的演示对象，不删除真实资料或历史结果。

**验收：** 干净库迁移、课程/资料删除、失败任务恢复和演示恢复均有明确操作记录；失败不污染新索引或覆盖旧完整索引。

### P7-4 成本、资源与请求限制

中期不追求吞吐量，优先控制“单机演示 + 小规模实验”的最坏情况。所有真实 embedding/LLM/Vision/reranker 调用仍遵守当次授权。

| 类别 | 中期策略 |
| --- | --- |
| Docling | 单机低并发，按页/文件范围处理；最小必要 extras/模型；记录下载体积、缓存体积、峰值 RAM、耗时 |
| Embedding | 固定模型与 batch；资料冻结后不因 UI/Prompt 小改反复全量 embedding |
| LLM | 固定题集、上下文上限、输出上限、超时和重试；评测达到预算即停止 |
| Vision | 默认关闭；只有固定少量视觉题在明确授权后调用，单独计量 |
| Reranker | 默认关闭；只有新 baseline 证明排序瓶颈后才启用 |
| API/文件 | 沿用现有文件大小、页数、问题长度、上下文和候选上限；UI 对用户可理解地提示主要限制 |

实际费用优先记录供应商响应中的 usage 或账单数据；没有可靠 usage 时不得猜算 token/费用。供应商价格和限流会变化，文档只保存本次实验实际采用的模型、版本、调用量和账单依据，不把历史价格写成永久合同。

### P7-5 运行、健康检查与 Demo 准备

1. 保持现有本机启动方式；补齐一份最短启动/检查顺序：数据库 → migration → backend → frontend → health/ready → 登录。
2. 健康检查只说明进程/数据库/配置状态，不把 configured 写成供应商连通或模型可用。
3. Demo 前固定课程、账号、资料和题目，避免临场重新解析、重新入库或临时换模型。
4. 准备“正常回答 + 引用核对”“资料外问题 → 依据不足”“服务异常 → 系统失败”“撤权/串课 → 拒绝访问”四类固定演示。
5. 录屏前重新登录、检查资料状态和数据库连接；不拍摄 key、Cookie、学生身份、原始答案或其他敏感内容。

### P7-6 中期交付分档

| 档位 | 中期范围 |
| --- | --- |
| **必须完成** | 四课资料可用主路径、课程/角色权限、资料上传与失败恢复、问答与引用核对、依据不足/系统失败区分、统一界面、基础教师反馈、数据库迁移与恢复说明、固定 Demo 流程 |
| **重点争取** | Dense/Hybrid 新基线、小规模 rerank 或 Vision 代表案例、课程编辑/删除 UI、解析质量展示、非开发者独立试用、Demo Reset |
| **中期后** | 更全面复杂资料、多轮/流式、学生自主选课、多人试用、远程部署、知识图谱、Agentic RAG、全量多模态索引等 |

中期验收的成功标准不是“所有功能完成”，而是核心闭环稳定且边界诚实：一个学生能在授权课程中得到有依据回答并回原页核对；教师能维护资料和成员；管理员能准备演示环境；出现无依据、越权、解析失败或服务失败时，系统能显示正确状态。

### R8/R9：内部验收、冻结与展示

R8 由用户与开发者共同操作真实版本，重点走：登录/课程权限 → 上传 → 解析任务 → 失败恢复 → 引用回答 → 原页核对 → 依据不足/系统失败 → 教师反馈 → 撤权/串课。实际发现的问题优先修复，再重复受影响验收。

R9 最后冻结代码、依赖、迁移、17 份资料、结构化解析产物、页级质量、题集、评测结果和恢复包，再制作 PPT、录屏和答辩材料。展示只说已经验证的能力，不把计划、模型宣传能力或旧 R7 数字写成当前结果。

### 明确不做

- 不整体迁移到 RAGFlow、Dify、Kotaemon、RAG-Anything、LangChain、LlamaIndex、Haystack 或 LightRAG。
- 不同时维护 Docling 和 MinerU 两套生产解析管线。
- 不下载 Docling 全部模型/extra，不默认启用 VLM、全量视觉描述或多模态索引。
- 不在解析尚未稳定时引入 GraphRAG、Agentic RAG、复杂 query decomposition 或新的知识图谱。
- 不为了“看起来技术多”提前加入 reranker；先让新的四课 dense/hybrid 基线成立。
- 不重新入库、跑评测或调用真实模型作为本次文档计划的一部分；这些均属于后续有授权的独立实施项。
