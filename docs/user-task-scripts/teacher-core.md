## T1 检查资料质量并决定下一步

目标：「查看两份资料是否可用，核对质量提示，指出各自需要怎样处理。」

步骤：进入「课程资料」→ 找到指定资料 → 分别看状态、参与问答检索、入库质量、失败原因 → 对已成功但带警告的 PDF 打开指定页并核查文字 → 解释两份资料的区别与下一步。

成功条件（全部满足）：

- 能说出 `succeeded` 且「部分页面需核对」/「文本较少」属于质量警告，已有索引不代表每页充分抽取；不能当整份入库失败，也不能凭文档级警告编造问题页码。
- 能把 `failed` /「暂不可用」与警告分开；失败不代表已成功获得完整新索引。先看原因并判断后续检查/安全重试方案，本任务只记录方案，不触发解析。
- 区分「停用检索」与删除/入库失败：停用保留资料与原文访问，但不参与新问答。实际打开成功带警告 PDF 的指定页并记录判断；不得把 API 的成功状态当成人工质量核验完成。

## T2 核查候选并保存处理动作（PLAN-05）

目标：「从本课问答反馈里选择指定候选，核对问句和相关资料，记录你的判断与一个备课动作。」

步骤：进入「问答反馈」→ 核对课程、统计窗口和样本数 → 看「主题候选」或「待处理线索」→ 对照代表问句、依据不足/系统失败分类与课程资料 → 说明是否支持候选及原因 → 在「教师处理记录」填处理对象（与候选原文对应）、意图、知识点（不确定可填待归类）、行动 → 点击「保存处理」→ 核对记录表新增行。

成功条件：知道 candidate 是待确认线索；不从高频问句推断学生能力，不从系统失败推断知识缺口；能用问句/资料说明判断；独立保存与同一对象对应的非空知识点和明确行动，表中值相符。「课堂澄清」「补充/澄清资料」「加入回归题集」「暂不处理」「排查系统失败」只记录意图，不自动改资料、加题、重入库或联系他人。

观察者实现边界：当前表单保存 `subject_type=clue`、`review_status=confirmed`、`cause_code=undecidable`；没有拒绝/暂缓状态及原因编辑控件。API 支持更多状态不代表 UI 已支持。若参与者拒绝候选或无法确认，记录原判断和界面限制，不能强迫保存为 confirmed 来凑完成；回流 PLAN-05 并在修复后复测。本轮 API 排练使用可确认的合成候选，只证明保存路径。

## T3 刷新后核查处理记录

目标：「确认刚才的处理记录在重新打开页面后仍然存在。」

步骤：记下 T2 新行的对象、意图、知识点、状态、行动 → 点「刷新记录」→ 浏览器刷新整页 → 回到同一课程的「问答反馈」→ 找到同一条记录并逐字段比对；若刷新导致重新登录，记录现象与恢复操作。

成功条件：两次刷新后记录都存在，字段与保存时相同，没有靠再次点击「保存处理」重新创建；记录证据。API 重新 GET（即使重登录/清 ORM 缓存）只证明后端持久化，不代替这项浏览器体验。
