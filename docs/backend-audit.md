# 阶段 26：Python 后端严格审计

## 1. Findings

### [P1] 删除后评测在 Top-K 之后才排除文档，可能高估拒答准确率

状态：阶段 27 已修复；旧阶段 24 报告仍是历史结果，尚未调用云服务重跑。

- 审计时证据（提交 `2783914`）：`backend/app/eval.py:117` 先调用 `retrieve_chunks` 得到已截断的 Top-K，随后才在 `backend/app/eval.py:118-122` 按文件名过滤 `excluded_documents`。
- 影响：被排除文档的切片仍会占据 Top-K 名额，其他仍存在的文档没有机会递补。所谓“删除后对照”并不等价于先删除文档再检索，可能把本应由剩余资料回答的问题误判为正确拒答。阶段 24 的删除后指标因此只能视为当前实现下的结果，不能作为严格删除仿真的最终证据。
- 测试缺口：`backend/tests/test_eval.py` 只覆盖题集校验、dry-run 和云调用开关，没有覆盖排除文档发生在检索前还是检索后。
- 建议验收：让文档排除条件进入检索查询与排序之前；构造“被排除文档占据原 Top-K、未排除文档可递补”的回归测试，然后重新运行阶段 24 真评测并保留新旧报告差异。

### [P1] 核心检索为全量拉取后在 Python 排序，pgvector 没有承担 Top-K

- 证据：`backend/app/services/retrieve.py:45-50` 把课程下所有兼容切片及向量加载到应用进程，`backend/app/services/retrieve.py:54-59` 逐条计算余弦相似度、全量排序后才截取 Top-K；`backend/app/services/retrieve.py:80-83` 的索引身份检查也会拉取全课程身份值。
- 影响：时间、内存和数据库传输量随课程切片数线性增长，排序为 `O(N log N)`；课件增多后，每次提问都会重复付出该成本。仓库虽然使用 Postgres + pgvector，但当前在线检索没有获得数据库向量检索的伸缩性。
- 测试缺口：现有检索测试验证正确性和课程隔离，没有查询规模、SQL 形态或索引使用证明。
- 建议验收：使用 pgvector 距离操作符在数据库内按课程、索引身份和排除文档过滤并 `ORDER BY ... LIMIT top_k`；身份不一致改为 `EXISTS` 查询；保留 Fake/SQLite 可测路径，增加 SQL/Postgres 集成证明和小型基准。

### [P2] 入库任务依赖进程内 BackgroundTasks，没有中断恢复

- 证据：`backend/app/api/documents.py:89-95` 先把任务写为 `pending`，再注册 FastAPI 进程内后台任务；`backend/app/services/ingest.py:39-41` 会把任务提交为 `running`。启动路径没有扫描或恢复遗留的 `pending/running` 任务。
- 影响：进程崩溃、开发热重载或主机重启发生在响应之后时，任务可能永久停在 `pending/running`，用户只能看到卡住状态，且没有重试入口。
- 建议验收：在不引入本期明确排除的 Celery 集群前，先实现可重复执行的恢复策略或受控重试端点，定义 stale-running 判定，并测试重复执行不会产生重复切片。

### [P2] 单个文件的所有切片一次性发送给向量服务

- 证据：`backend/app/services/ingest.py:45-50` 先生成全部切片，再通过一次 `embedder.embed([...])` 请求发送；上传上限为 `backend/app/api/documents.py:33` 的 15 MiB。
- 影响：较大 Word/PDF/PPT 文件可能超过供应商单次输入数量或 token 限制，也会放大内存峰值、超时和整批重试成本。
- 建议验收：按可配置批大小嵌入，逐批校验维度；明确失败时的事务语义，并用 FakeEmbedder 记录批次大小验证边界与失败回滚。

### [P2] 数据库删除与上传文件生命周期没有形成统一边界

- 证据：上传在 `backend/app/api/documents.py:77-80` 先落盘、`backend/app/api/documents.py:92` 后提交数据库，提交失败没有清理文件；课程删除在 `backend/app/api/admin_courses.py:88-90` 只删除数据库记录，没有清理该课程上传目录；单文档删除的 `backend/app/api/documents.py:124-130` 直接信任数据库中的 `storage_path`，没有验证解析后的路径位于 `settings.upload_dir` 内。
- 影响：上传或课程删除后可能留下孤儿文件；若数据库记录被迁移脚本、人工操作或缺陷写成越界路径，删除资料可能误删上传根目录之外的本机文件。正常 API 生成的路径是受控的，但删除边界仍应自我校验。
- 建议验收：集中实现受 upload root 约束的存储服务；验证 `resolve()` 后的目标仍在根目录内；为上传提交失败、单文档删除和课程级清理补测试，并明确数据库成功但文件清理失败的告警与补偿策略。

### [P2] 真评测缺少增量落盘，且一个失败类型实际上不可达

状态：阶段 27 已修复失败分类；增量落盘仍待后续阶段处理。

- 审计时证据（提交 `2783914`）：`backend/app/eval.py:114-153` 在内存中完成全部 case；任一云调用抛错时，`backend/app/eval.py:207` 不能返回，最终的 `backend/app/eval.py:217-218` 不会写报告。另有 `actual_refusal = mismatch or not reliable`（`backend/app/eval.py:132`），因此回答题无合法引用时会先命中 `unexpected_refusal`（`backend/app/eval.py:135-136`），后面的 `missing_valid_citation`（`backend/app/eval.py:139-140`）不可达。
- 影响：长评测在末尾失败会丢失此前已付费完成的结果，重跑增加成本；失败分类不能准确区分检索后无合法引用，削弱调参诊断价值。
- 建议验收：每题原子追加或周期性 checkpoint，保留失败题及安全错误摘要；重排失败分类并用表驱动测试覆盖每个枚举值。

### [P3] 过期 Session 只判无效，不回收记录

- 证据：`backend/app/security/sessions.py:50-57` 发现过期记录后直接返回 `None`，没有删除或周期清理。
- 影响：长期运行时 Session 表持续增长。当前本机演示风险较低，但正式部署前应处理。
- 建议验收：增加定期清理或登录时限量清理，并对 `expires_at` 建索引；不要在每个请求上做无界删除。
