# 教师侧课程问答分析 Agent：设计与开工笔记

> 用途：供后续开发 Bot 落地教师侧辅助分析功能。本文件是**设计约定与实施目标**，不是当前代码已经完成的功能清单。开工前先核对现有问答日志、教师权限、检索接口和教师反馈页面，沿用项目既有约定；不必为此重构主系统。

## 1. 定位与优先级

项目的主体是**三角色课程业务、资料管理与知识库、RAG 问答和引用溯源**。先打通管理员管理课程与成员、教师管理资料与反馈、学生授权问答并点击引用回到原文的完整演示路径，同时推进资料解析与检索增强。

Agent 是教师端的一项轻量扩展，只解决一个问题：**根据本课程的学生提问，归纳常见疑问，关联课程资料，生成可核对的备课参考。**

- 实现策略：**单 Agent / 单任务入口 / 有限分支 / 两类只读工具 / 复用现有 RAG**。
- 交付目标：一个可完成、可复现、可测试的综合分析任务，而不是通用智能助理平台。
- 不列入首期：多 Agent、自由循环规划、长期记忆、任意 SQL 或文件操作、自动修改课程/成员/成绩、复杂断点续跑、另一套知识库和检索管线。
- Agent 与主线分开验收；主线演示不依赖 Agent 是否运行成功。

## 2. 核心使用场景与教师界面

教师进入自己有权限的课程 → 打开「问答分析」→ 选择时间范围（建议预置近 7 天 / 14 天 / 30 天）→ 使用自然语言提出分析需求，如：

> 汇总这门课最近两周学生经常问的问题，找出相关课件，并整理下节课可以重点讲解的内容。

首期以这类**综合分析任务**为唯一完整验收场景；“只看常见问题”“查相关课件”“给复习建议”可以复用同一流程的输出模块，不必建设三个独立 Agent。

结果页面使用普通信息卡/区块展示：

1. **数据范围与样本说明**：课程、起止时间、范围内总问句数、实际参与语义分析的问句数。
2. **常见问题**：建议最多 3 个主题，每个主题提供代表性匿名原始问句、纳入该主题的样本问句数。
3. **课程依据**：每个主题展示匹配到的课件标题、引用摘录、PDF 页码及原文跳转；没有可靠依据时标明“未找到足够的课程资料”。
4. **备课参考**：建议讲解的知识点、可使用的代表性学生问题，以及对应资料；作为教师参考，不推断个人学习水平。
5. **运行状态**：分析中、成功、部分完成或失败；有明确的错误提示和重新执行入口。

教师仍可按原流程使用课程反馈统计表；Agent 只是帮助将统计、问句和课件依据组织成一份容易阅读的分析。

## 3. 最小工作流

```text
教师当前登录会话 + 当前课程 + 时间范围 + 自然语言需求
        ↓
后端鉴权并校验课程、时间范围、支持的任务类型
        ↓
工具 A：读取本课问答记录 + 计算确定性统计
        ↓
LLM：将样本问句归纳为最多 3 个主题，给出引用的问句 ID 和检索关键词
        ↓
程序校验：主题关联的问句 ID 必须来自本次允许的数据集；
          重算每类的样本数量并检查样本覆盖说明
        ↓
工具 B：针对主要主题调用现有 RAG 检索，获取真实资料引用
        ↓
LLM：依据统计、原问句和可靠资料，生成结构化备课参考
        ↓
后端验证输出引用、存储任务结果 → 教师查看/重试
```

首期优先使用固定流程与少量分支：对于“只看提问归纳”的需求可以跳过课程资料关联；需要教学建议时才走完整流程。模型辅助识别意图、归纳主题、提出检索词和组织文字；**数据库统计、工具执行、权限与运行边界由后端负责**。

如现有项目的 LLM 适配层已经提供结构化输出或工具调用能力，直接复用；无需为了此功能单独接入 LangGraph。

## 4. 两类工具的职责与返回值

### 工具 A：读取课程问答与统计

建议内部抽象为 `query_course_questions(course_id, start_at, end_at, limit)`。具体函数名、数据库模型和 API 路径以现有工程为准。

- 只查本课程、所选时间范围内可供教师查看的学生提问；后端根据登录教师会话校验成员关系。
- 后端统计该范围的真实问句总数；在必要时按标准化文本计算重复问句出现次数。
- 给模型的问句取稳定 ID、内容、时间等最小必要字段；避免携带学生身份、邮箱或会话 Cookie。
- 建议首期**最多分析 100 条问句样本**；超过上限时按确定性规则取样，并明确标注“总量统计”和“样本主题归纳”的区别。不要把样本主题数量写成全部问答的分布。
- 无法可靠归类的问句归入“其他/未分类”；仅展示最多 3 个主要主题，确保样本覆盖数量能对账。
- 空数据返回正常的空结果及提示；模型不能虚构问句。

示意返回：

```json
{
  "course_id": "<服务端已授权课程>",
  "range": {"start_at": "...", "end_at": "..."},
  "total_questions": 183,
  "sample_count": 100,
  "sample_method": "recent_100",
  "questions": [
    {"id": "q101", "text": "梯度下降的学习率如何选？", "created_at": "..."}
  ]
}
```

其中数字仅作字段示例，不是项目现有数据。

### 工具 B：检索本课知识库

建议内部抽象为 `search_course_evidence(course_id, query, top_k)`，直接复用现有课程过滤、索引状态、检索和引用处理。

- 由程序把检索强制限定在当前授权课程；模型仅能提供主题检索词。
- 默认最多检索 3 个主题，每个主题最多保留 3 条候选证据；实际参数可在实现时集中配置。
- 结果至少应具备可核验的文档标识、标题、摘录，以及支持时的 PDF 页码与跳转所需信息。
- 应以既有证据筛选机制决定能否用于最终报告；不能把相关性弱的召回结果自动视为可靠依据。
- 检索失败或无足够依据时，保留问句统计，标注对应主题资料不足。

这里与主线的 OCR、混合检索、重排及引用定位增强复用同一套能力，Agent 不维护第二份索引，也不自行生成“来源页码”。

## 5. 结构化结果约定

输出建议采用 Pydantic 模型校验，字段名可依据代码风格调整，至少表达：

```text
AnalysisResult
  course_id
  time_range
  total_questions             # 全量范围内由数据库统计
  sampled_questions           # 实际进入语义分析的样本量
  sample_note                 # 样本量不足/截断说明
  topics[]:
    topic_name
    question_ids[]            # 必须属于该次授权查询结果
    sample_question_count     # 由后端计算，不信任 LLM 数值
    representative_questions[]# 匿名、可追溯到原问句
    evidence[]                # 来自真实 RAG 检索结果
  teaching_suggestions[]      # 有依据的教学参考
  limitations[]               # 数据不足、未命中课件等
```

LLM 只返回受控 JSON，不负责写入数据库统计值和文档链接。若主题归类存在无效 ID，拒绝该组或修正为已确认的合法关联；若无法证明建议所依据的课件内容，降低为“根据提问情况建议复习”的一般性提醒并明确说明依据范围，避免杜撰具体知识结论。

## 6. 权限、状态和失败处理

- **权限**：复用现有 Cookie Session/课程成员鉴权；教师仅分析自己有权限的课程。每个服务端工具都重新检查权限，忽略模型试图更换课程或调用未定义功能的要求。
- **输入边界**：长度、时间跨度、样本数量、检索主题数均设上限；模型的任务解释只用于允许范围内的分支选择。
- **不可信内容**：学生问句及课件文本只作为数据，不作为 Agent 指令。生成结果不附带个人学生表现排名。
- **状态**：可用 `pending → running → succeeded / partial / failed` 的简单状态记录，保存开始/结束时间、步骤是否成功、错误摘要与结果引用。沿用现有日志/任务表的可能性须由 Bot 核查。
- **重试**：首期失败后允许重新运行整项任务；不开发复杂 checkpoint、长任务恢复或消息队列。
- **部分完成**：只有后端统计确实成功时才可展示该部分；模型、检索服务故障明确说明，不能展示伪造的完整分析。
- **脱敏**：执行日志仅记录必要的标识、耗时、失败类型，不记录密钥、完整敏感请求或学生身份信息。

## 7. 前后端集成建议

尽量复用现有教师课程页、问答日志接口、RAG 服务、权限依赖和引用跳转组件。不要先为了 Agent 建一个通用框架。

首期只需要：

1. **教师页入口**：选当前课程及时间范围，填写/选择任务请求，提交后显示状态。
2. **一个分析任务服务**：授权 → 查询 → 归纳 → 检索 → 生成 → 校验；可以同步执行或按项目现有异步/任务模式接入。
3. **结果查询与展示**：主题、代表问句、课件引用、备课建议、失败提示和重试。
4. **少量运行记录**：足够排错与复现实验；不另开发监控仪表板。

如需新增 API，可考虑“创建分析任务 / 查询任务结果”的形式；**路径、数据库表和接口签名须在核对现有实现后再确定**，避免与已存在的反馈/洞察接口重复建设。

## 8. 可开工的开发顺序与验收

### 0. 先确认依赖（只读排查）

由 Bot 核对：问答日志字段及保留策略、教师对日志的访问授权、是否已有问句分组/洞察表、RAG 检索函数和引用结构、教师页面入口、LLM 结构化输出适配、现有测试机制。形成一页映射表，列出可复用模块与确需新建的最小内容。

### 1. 第一个可验收的最小版本

完成教师鉴权后的问句查询和准确统计 → 模型归纳主题 → 结构化结果与基本页面；提供空数据和越权用例。此时暂不生成课件建议，先保证数据真实。

### 2. 补上课程依据与教学参考

将主题检索词传给现有 RAG，返回真实引用，生成少量备课建议，完成教师端引用回跳；无命中时正确说明资料不足。

### 3. 最后补异常处理与回归

加入耗时与调用上限、运行摘要、失败提示、重新执行；按固定数据验证整条链路，并确认没有影响既有学生问答和教师反馈。

**最低验收清单**：

- [ ] 教师只能分析授权课程；学生及无权限用户被拒绝。
- [ ] 时间范围过滤准确，数据库统计与实际记录对得上。
- [ ] 主题中的问句 ID 均来自当前授权查询，样本统计不冒充全量。
- [ ] 原始问句可核对，输出不展示学生个人身份。
- [ ] 课件标题、摘录、页码来自现有检索结果，引用能回跳。
- [ ] 无对应课程资料时有明确说明，不杜撰来源。
- [ ] 无问答记录、样本很少、超时、模型失败、检索失败均有合理终态。
- [ ] 固定演示用例至少覆盖“完整成功”和“资料不足”两条路径。
- [ ] 原有三角色业务、知识库和 RAG 问答回归测试通过。

建议准备约 10—12 条 Agent 任务用例，以预设数据集核对统计和引用结果；Agent 验收与主 RAG 问答题集分别记录。

## 9. 结题演示方案

先演示三角色业务：管理员管理课程和成员 → 教师上传/管理资料并查看反馈 → 学生在授权课程问答并点击引用回到 PDF 原页。此流程应独立稳定。

随后在教师端选择**提前准备、明确标记的演示问答数据**，运行一条固定的分析请求，展示问题主题、代表问句、课件引用和备课建议。事先保存一次标注为“历史成功结果”的真实运行记录，用于现场模型服务异常时展示既有成果，不将回放冒充实时生成。

演示最重要的是：老师可以清楚看到**数据从哪里来、课程依据在哪里、教师怎样使用结果**。Agent 的复杂技术细节留在开发笔记和测试记录中，避免影响教学业务主线。

## 10. 给开发 Bot 的最终约束

本笔记不代表已经完成实现，也不规定必须新增哪些数据库表或依赖。Bot 开工时先核查现有代码，优先复用成熟接口，按**查询统计 → 主题归纳 → RAG 证据关联 → 结果展示 → 异常验收**逐项完成。每项提供测试记录和简短交接说明。若发现现有能力与本文设想不一致，应优先采用更简单、与现有工程兼容的实现，记录差异，而不是为匹配笔记重构项目。
